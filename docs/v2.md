# Sancho Version 2 Planning

This document records potential tool-calling capabilities for a future V2. It is a planning document only. V1 remains an offline-first local chat application and does not execute model-requested tools.

## V2 goal

V2 may allow the local Gemma model to request narrowly defined tools. Sancho, not the model, will validate and execute each request, return a bounded result to the model, and continue the conversation.

The initial V2 priority is controlled internet access. Phone actions, terminal commands, and remote administration come later and require stronger confirmation gates.

## Tool-calling lifecycle

```text
User prompt
    -> local model receives approved tool declarations
    -> model emits a structured tool call
    -> Sancho validates the tool name and arguments
    -> Sancho asks for confirmation when the risk requires it
    -> an executor runs the tool with limits
    -> Sancho returns a bounded tool result to the model
    -> model produces the final response
```

Gemma function calling does not execute code by itself. The application must parse, validate, and execute the generated call. See the [Gemma 4 function-calling guide](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4).

## Candidate tool transports

### Native HTTPS tools — preferred first implementation

Implement small, explicit Android tools inside Sancho:

- `search_web(query)`;
- `fetch_web_page(url)`;
- later, narrowly scoped APIs such as weather or public transport.

The model remains local while only the selected tool uses the network. The AI profile must have GrapheneOS Network permission enabled. Responses should be normalized to text, capped by bytes and elapsed time, and labeled with the source URL.

This is the preferred V2 internet path because it has the smallest number of moving parts and gives Sancho direct control over permissions, validation, redaction, and user confirmation.

### MCP over HTTPS — future tool ecosystem

Sancho could act as an MCP client and connect to a trusted MCP server on a home computer, local network, or remote host. This could expose web search, remote files, SSH, or other tools through one protocol.

Streamable HTTP is the preferred transport for remote MCP servers. Authentication, certificate validation, server allowlists, tool allowlists, and network failure handling would be required before enabling it. See the [MCP transport documentation](https://ts.sdk.modelcontextprotocol.io/server).

### GrapheneOS Terminal VM — experimental command environment

The GrapheneOS Terminal provides a Debian-based Linux development environment inside a virtual machine. It is useful for manually experimenting with `curl`, Python, SSH, and other Linux tools.

The current Android implementation exposes a terminal activity, but there is no documented stable third-party command-execution API for Sancho. The terminal should therefore be treated as a manual development environment, not as a V2 executor, unless GrapheneOS or Android later provides a supported integration surface.

References: [Android Linux development environment](https://source.android.com/docs/core/virtualization/usecases), [GrapheneOS releases](https://grapheneos.org/releases).

### Termux `RUN_COMMAND` — prototype command bridge

Termux can provide OpenSSH, `curl`, Python, and other command-line tools. Sancho can request commands through Termux's `RUN_COMMAND` interface.

This requires the AI profile to grant Sancho Termux's command permission and requires Termux's external-command policy to be enabled. Because this can become arbitrary shell execution, the first prototype must call one fixed wrapper or allowlisted command set rather than passing raw model text to a shell.

Reference: [Termux RUN_COMMAND intent](https://github.com/termux/termux-app/wiki/RUN_COMMAND-Intent).

### Browser handoff — user-controlled research

Sancho may open a search URL or page in Vanadium through an Android browser intent or Custom Tab. This is useful when the user needs to log in, solve a CAPTCHA, or inspect a page manually.

It is not a reliable autonomous tool because the browser does not return a structured result to Sancho.

### SSH remote gateway — remote execution

Sancho could connect to a trusted computer or server over SSH and request a small set of remote operations. This is useful when the remote machine already has web tools, files, or development services.

The implementation would need host-key pinning, encrypted key storage, command allowlists, timeouts, output limits, and explicit confirmation for mutations.

### Embedded SSH libraries — native remote tool

Instead of launching another SSH app, Sancho could embed an SSH client library:

- [`cbssh`](https://github.com/connectbot/cbssh) for SSH, shell sessions, SFTP, and port forwarding;
- [`termlib`](https://github.com/connectbot/termlib) if Sancho later needs a native terminal surface.

This provides more control than an external app, but makes Sancho responsible for host-key verification, key management, connection lifecycle, and remote-command safety.

## Candidate V2 tools

### Internet and information

- `search_web(query)` — search approved web providers;
- `fetch_web_page(url)` — retrieve and normalize an approved HTTPS page;
- `extract_page_text(url, selector?)` — optional constrained extraction;
- `read_local_document(uri)` — read only a user-selected document;
- `calculate(expression)` — local deterministic calculation without network access.

### Remote and terminal actions

- `ssh_exec(host_id, command_id)` — execute an allowlisted operation on a saved host;
- `ssh_read_file(host_id, path)` — read a user-approved remote file;
- `sftp_upload(host_id, local_uri, remote_path)` — require confirmation;
- `terminal_run(script_id, arguments)` — call an approved local wrapper, never arbitrary model text;
- `list_remote_hosts()` — return host labels without exposing private keys.

### Phone-local actions

- `read_selected_file(uri)` — only after Android's document picker returns a URI;
- `create_note(title, body)` — require confirmation before writing;
- `share_text(text)` — always show the Android share sheet;
- `take_photo()` — require foreground user interaction;
- `open_url(url)` — use browser handoff rather than silent navigation.

## Security requirements

Every tool should have a schema, risk level, timeout, output limit, and executor-owned implementation.

- The model cannot select an unknown tool.
- Tool arguments are validated independently of the model output.
- Network tools use HTTPS and an explicit host policy.
- Search and fetch results are treated as untrusted input and never as instructions.
- Mutating, remote, or shell-like actions require visible confirmation by default.
- Credentials and private keys stay outside prompts, logs, and model-visible tool results.
- Tool output is truncated and marked when incomplete.
- Each execution records tool name, timestamp, duration, result status, and a redacted summary.
- V2 must work when all optional tools are disabled; local chat remains available.

## Proposed V2 phases

1. Define `ToolSpec`, typed arguments, validation, execution results, and confirmation states.
2. Add mock tools and deterministic tests without network access.
3. Add native `search_web` and `fetch_web_page` with a visible network indicator.
4. Add tool-result conversation formatting and bounded streaming resumption.
5. Evaluate MCP over HTTPS for remote, user-managed tool servers.
6. Prototype Termux or SSH only behind explicit allowlists and confirmation.
7. Consider embedded SSH support after the tool policy and credential model are stable.

## V1 boundary

The following remain outside V1:

- model-requested network access;
- MCP clients or servers;
- Graphene Terminal or Termux command execution;
- SSH, SFTP, or remote administration;
- unrestricted shell access;
- background tool execution without visible user consent.
