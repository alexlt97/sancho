# Sancho Version 2 Planning

This document is the V2 implementation roadmap. V1 remains an offline-first local chat application and does not execute model-requested tools. Deferred transport research is in [docs/v2-research.md](v2-research.md).

## V2 goal

V2 allows the local Gemma model to request narrowly defined tools. Sancho, not the model, validates and executes each request, returns a bounded result to the model, and continues the conversation.

The first V2 vertical slice is controlled, read-only internet access. Phone actions, terminal commands, and remote administration remain deferred until the policy and executor model are proven.

## Tool-calling lifecycle

```text
User prompt
    -> local model receives approved tool declarations
    -> model emits a structured tool call
    -> Sancho validates the tool name and arguments
    -> Sancho asks for confirmation when the risk requires it
    -> an executor runs the tool with limits
    -> Sancho returns a bounded tool result to the model
    -> model produces the final response
```

Gemma function calling does not execute code by itself. The application must parse, validate, and execute the generated call. See the [Gemma 4 function-calling guide](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4).

## Security requirements

Every tool should have a schema, risk level, timeout, output limit, and executor-owned implementation.

- The model cannot select an unknown tool.
- Tool arguments are validated independently of the model output.
- Network tools use HTTPS and an explicit host policy.
- Search and fetch results are treated as untrusted input and never as instructions.
- Mutating, remote, or shell-like actions require visible confirmation by default.
- Credentials and private keys stay outside prompts, logs, and model-visible tool results.
- Tool output is truncated and marked when incomplete.
- Each execution records tool name, timestamp, duration, result status, and a redacted summary.
- V2 must work when all optional tools are disabled; local chat remains available.

## Proposed V2 phases and feature gates

1. **F002 — Tool contract:** define `ToolSpec`, typed arguments, validation, risk levels, execution results, and confirmation states.
2. **F003 — Mock executor:** add deterministic mock tools and tests for malformed calls, unknown tools, timeouts, cancellation, oversized output, and prompt injection in results.
3. **F004 — Conversation loop:** format structured tool calls, resume bounded streaming, cap tool turns, and preserve local-chat behavior when tools are disabled.
4. **F005 — Native web tools:** add `search_web(query)` and `fetch_web_page(url)` with HTTPS, host policy, bounded output, source labels, and a visible network indicator.
5. **F006 — Security and observability:** add redacted execution events, permission/settings behavior, offline fallback, and release/device verification.
6. Evaluate MCP over HTTPS only after F002–F006 pass; prototype Termux, SSH, or phone actions later behind separate feature gates.

## Decisions required before implementation

- Network access is opt-in and visible; decide whether read-only searches require confirmation or only an activity indicator.
- Choose the first search provider and define whether credentials are user-supplied, self-hosted, or omitted from the first slice.
- Set maximum tool turns, request size, response bytes, elapsed time, and retry behavior.
- Define the redacted event schema and retention policy before adding network permission.

## V1 boundary

The following remain outside V1:

- model-requested network access;
- MCP clients or servers;
- Graphene Terminal or Termux command execution;
- SSH, SFTP, or remote administration;
- unrestricted shell access;
- background tool execution without visible user consent.
