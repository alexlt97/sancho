# Sancho Version 2 Planning

This document is the V2 implementation roadmap. V1 remains an offline-first local chat application and does not execute model-requested tools. Deferred transport research is in [docs/v2-research.md](v2-research.md).

## V2 goal

V2 extends the local Gemma model with an offline voice conversation surface and, later, narrowly defined tools. Sancho, not the model, validates and executes each tool request, returns a bounded result to the model, and continues the conversation.

The first V2 vertical slice is an offline voice conversation. Controlled, read-only internet access follows it. Phone actions, terminal commands, and remote administration remain deferred until the policy and executor model are proven.

## First V2 vertical slice: offline voice conversation

The initial voice architecture is intentionally compositional:

- Speech-to-text: use embedded [Moonshine Voice](https://github.com/moonshine-ai/moonshine) `MicTranscriber` with a user-imported streaming model. Tiny Streaming remains the default for responsiveness, while Small Streaming is available as an experimental accuracy option. Sancho owns microphone capture and receives partial/final transcript callbacks without launching FUTO or another recognition surface.
- Reasoning: send the returned transcript through Sancho's existing LocalLlm text path using the installed Gemma 4 E2B model.
- Response: use Android TextToSpeech with an installed offline voice. Generated text remains available for the normal chat surface, but the voice surface speaks it by default.
- Entry point: a home-screen widget or Quick Settings tile starts a dedicated voice session through an explicit `VoiceSessionActivity` launch. The main chat activity does not open for the normal voice loop; the dedicated surface shows an animated phase bubble while Moonshine, Gemma, and TextToSpeech work.
- Privacy: no network speech fallback, no retained microphone recording, and all providers must be available in the AI GrapheneOS profile. The APK declares only `RECORD_AUDIO` for this embedded voice path; Moonshine's optional network/downloader permissions are removed from the merged manifest.

Direct Gemma audio input remains an experiment. Gemma 4 E2B supports audio ASR, but the current Sancho adapter sends only text and images and imports .litertlm models; it does not yet expose an audio content path. We will benchmark a compatible audio-enabled LiteRT-LM bundle separately before considering it as a speech provider.

## Role-specific model harness

Sancho keeps model behavior separate from the repository's developer contract in
`app/src/main/assets/prompts/`. A common privacy policy is combined with one
role profile and supplied as LiteRT-LM's `ConversationConfig.systemInstruction`.

- **Chat/Vision:** accepts text and images, can use Markdown and equations, and
  does not request tools in this iteration.
- **Voice/Agent:** treats input as an offline speech transcript, produces short
  speech-friendly text, avoids Markdown, and remains tool-free until the tool
  contract and executor are implemented.

The model binary is shared, but the roles use separate conversations and
instructions. `AGENTS.md` is not model input. It remains a Codex/developer
contract. Tool capability is application-owned and cannot be granted by a
prompt file.

## Tool-calling lifecycle

The first implementation slice is the typed boundary documented in [V2 tool
contract](tool-contract.md). It validates a proposed `open_web_search` call,
pauses ChatViewModel for confirmation, launches an approved Brave Search URL in
Vanadium, and exposes an opt-in manual LiteRT-LM event loop with confirmation
and tool-turn limits. Chat Settings can instead route the approved request to a
configured SearXNG HTTPS endpoint or the authenticated Brave Search API;
arbitrary page fetching remains deferred.

```text
User prompt
    -> local model receives approved tool declarations
    -> model emits a structured tool call
    -> Sancho validates the tool name and arguments
    -> Sancho asks for confirmation when the risk requires it
    -> an executor runs the tool with limits
    -> Sancho returns a bounded tool result to the model
    -> model produces the final response
```

Gemma function calling does not execute code by itself. The application must parse, validate, and execute the generated call. See the [Gemma 4 function-calling guide](https://ai.google.dev/gemma/docs/capabilities/text/function-calling-gemma4).

## Security requirements

Every tool should have a schema, risk level, timeout, output limit, and executor-owned implementation.

- The model cannot select an unknown tool.
- Tool arguments are validated independently of the model output.
- Network tools use HTTPS and an explicit host policy.
- Search and fetch results are treated as untrusted input and never as instructions.
- Mutating, remote, or shell-like actions require visible confirmation by default.
- Credentials and private keys stay outside prompts, logs, and model-visible tool results.
- Tool output is truncated and marked when incomplete.
- Each execution records tool name, timestamp, duration, result status, and a redacted summary.
- V2 must work when all optional tools are disabled; local chat remains available.

## Proposed V2 phases and feature gates

1. **F007 — Moonshine speech adapter:** receive partial and final transcripts through the embedded local model, handle microphone permission, cancellation, model absence, and provider errors, and keep the path offline.
2. **F008 — Voice session:** connect transcript → local Gemma text inference → Android TextToSpeech, with explicit listening, thinking, speaking, and cancellation states.
3. **F009 — Voice entry points:** add a compact 1×1 Sancho widget and a Quick Settings tile that launch the same silent voice session, with AI-profile/device verification.
4. **F002 — Tool contract:** define ToolSpec, typed arguments, validation, risk levels, execution results, and confirmation states.
5. **F003 — Mock executor:** add deterministic mock tools and tests for malformed calls, unknown tools, timeouts, cancellation, oversized output, and prompt injection in results.
6. **F004 — Conversation loop:** format structured tool calls, resume bounded streaming, cap tool turns, and preserve local-chat behavior when tools are disabled.
7. **F005 — Native web tools:** add search_web(query) and fetch_web_page(url) with HTTPS, host policy, bounded output, source labels, and a visible network indicator.
8. **F006 — Security and observability:** add redacted execution events, permission/settings behavior, offline fallback, and release/device verification.
9. Evaluate direct Gemma audio, MCP over HTTPS, Termux, SSH, or phone actions only after the relevant earlier gates pass and each receives a separate feature gate.

## Voice cancellation design

The current voice slice keeps the dedicated activity open after the answer and uses the central phase sphere as its primary control: tapping it cancels an active session and starts the next prompt from Ready or Error. Exit-to-home remains a secondary text action. The next cancellation change should:

- keep the current generation coroutine cancellable while collecting the local model stream;
- stop Android TextToSpeech immediately when cancellation is requested;
- expose one Stop action through a low-noise ongoing notification while the model is generating or speaking;
- update the widget and Quick Settings tile state to show Listening, Thinking, Speaking, or Stopped;
- avoid a persistent notification permission until the notification path is implemented and explained to the user.

Exit removes the voice task and returns to the launcher rather than revealing
the main chat activity. Tapping the sphere from Ready begins a new Moonshine
recognition request in the same voice activity and resets the timing recorder.

The notification is preferable to making a second tap on the activity the primary stop mechanism: it remains available when the voice surface is not visually present and gives Android an explicit user-visible control for an active operation.

## Decisions required before implementation

- Network access is opt-in and visible; decide whether read-only searches require confirmation or only an activity indicator.
- Choose the first search provider and define whether credentials are user-supplied, self-hosted, or omitted from the first slice.
- Set maximum tool turns, request size, response bytes, elapsed time, and retry behavior.
- Define the redacted event schema and retention policy before adding network permission.

## V1 boundary

The following remain outside V1:

- model-requested network access;
- MCP clients or servers;
- Graphene Terminal or Termux command execution;
- SSH, SFTP, or remote administration;
- unrestricted shell access;
- background tool execution without visible user consent.
